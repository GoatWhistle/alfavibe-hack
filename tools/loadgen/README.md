# Нагрузочный стенд

Воспроизводит методику Приложения B ТЗ: датасет обрабатывается парами запросов
с одним `payload_id` (прямой шаг — маскирование, обратный — демаскирование),
считаются латентность, доля успешных ответов и точность восстановления.

## Быстрый старт

```bash
tools/loadgen/run.sh                 # smoke + target (RPS 1000)
tools/loadgen/run.sh all             # все профили
tools/loadgen/run.sh large           # только крупные тексты
SKIP_BUILD=1 tools/loadgen/run.sh …  # не пересобирать (release с LTO — минуты)
URL=http://host:8080 tools/loadgen/run.sh target   # внешний стенд, свой сервис не поднимаем
```

Скрипт поднимает сервис на `config/loadtest.yaml`, дожидается `/health/live`,
гоняет профили и складывает отчёты в `target/loadtest/*.json`, лог сервиса —
в `target/loadtest/server.log`.

## Профили

| Профиль | Нагрузка | Что проверяет |
|---|---|---|
| `smoke` | 50 RPS, 10 с | стенд жив, контракт отвечает |
| `target` | 1000 RPS, 60 с | целевой режим ТЗ: RPS 1000 при latency ≤ 1 с |
| `stress` | 2000 RPS, 60 с | п. 6 ТЗ: RPS 2000 при latency ≤ 1 с |
| `ceiling` | 6000 RPS, 30 с | где начинает ломаться латентность |
| `large` | 20 RPS, тексты по 100 000 токенов | п. 4.4 ТЗ: крупные массивы текста |
| `ratelimit` | 1000 RPS в систему с лимитом 200 | 429 с `Retry-After` вместо 5xx и зависаний |

Вердикт считает `verdict.py`: для обычных профилей — успешных ≥ 99% и p99 ≤ 1 с,
для `ratelimit` — наличие 429 при отсутствии 5xx и таймаутов.

## Генератор напрямую

```bash
./target/release/loadgen --rps 1000 --duration 60s \
  --system-id crm-assistant --system-key loadtest-key \
  --dataset tools/loadgen/datasets/mixed.jsonl --json report.json
./target/release/loadgen --help
```

Модель нагрузки открытая: запросы уходят по расписанию независимо от того,
ответил ли сервис на предыдущие. При закрытой модели замедление сервиса
маскируется замедлением генератора, и p99 получается заниженным.

Поведение под отказами повторяет проверяющую систему: таймаут запроса 10 с,
до 2 ретраев, 429 не считается невалидным ответом и не сбрасывает счётчик,
после 5 невалидных ответов подряд прогон останавливается.

`--mode` выбирает форму контракта:

- `native` (по умолчанию) — текущий контракт сервиса,
  `{"operation":"mask","text":…}` → `{"text":…,"session_id":…}`;
- `tz` — контракт Приложения A, `{"payload":…,"payload_id":…}` → `{"result":…}`.

Заголовки аутентификации уходят, если задан `--system-key`; пустой ключ проверяет
анонимный доступ, которым пользуется проверяющая система.

`--min-tokens N` раздувает каждый текст датасета повтором до N токенов —
так профиль `large` получает 100 000 токенов из трёх коротких строк без
хранения многомегабайтных файлов в репозитории.

## Датасеты

`datasets/mixed.jsonl` — 41 пример по категориям ПД из п. 4.1 ТЗ плюс сложные
предложения, негативные примеры (Пушкин, офис банка, номер договора) и тексты
без ПД. `datasets/large.jsonl` — три длинных фрагмента для профиля `large`.

Формат строки: `{"id": "…", "category": "…", "text": "…"}`. Строки, начинающиеся
с `#`, игнорируются. Категория попадает в разбивку отчёта, так что новые наборы
удобно добавлять целыми категориями.

## Базовые замеры

Apple M4, 10 ядер, macOS 26.2, rustc 1.89, release с fat LTO, сервис и генератор
на одной машине, `vault.mode: memory`, NER отключён, логирование `info` в файл,
режим `tz` (контракт Приложения A).

| Профиль | Достигнуто | mask p50 / p99 | demask p50 / p99 | Успешных |
|---|---|---|---|---|
| `target` | 1000 RPS, 17 800 токенов/с | 0.6 / 1.8 мс | 0.2 / 0.6 мс | 100% |
| `stress` | 1999 RPS, 35 600 токенов/с | 0.4 / 1.5 мс | 0.2 / 0.6 мс | 100% |
| `ceiling` | 5997 RPS, 106 800 токенов/с | 0.1 / 0.4 мс | 0.1 / 0.3 мс | 100% |
| `large` | 100 000 токенов на запрос | 124 / 136 мс | 9.5 / 11 мс | 100% |
| `ratelimit` | 704 RPS сквозь лимит 200 | — | — | 5926 × 429 |

Цель ТЗ (1000 RPS при latency ≤ 1 с) берётся с запасом почти на порядок: на 6000
RPS очередь не растёт, p99 остаётся меньше миллисекунды. Тексты на 100 000
токенов обрабатываются за ~136 мс на p99, то есть требование п. 4.4 выполняется
в пределах общего SLA.

Разбивка по категориям в отчёте показывает и качество: `masked%` — доля текстов,
которые маскирование изменило, `restored%` — доля точных восстановлений.
У категорий `clean` и `negative` `masked%` равен нулю по построению: это тексты
без ПД и упоминания, которые маскировать не нужно (Пушкин, адрес отделения
банка, номер договора).
