# Ревью решения PD-Guard (маскирование/демаскирование ПД для LLM)

Дата: 2026-09-23. Ветка: `master`. Объём: ~7.7 тыс. строк Rust, 26 тестов.
Проверено: чтение всего исходного кода, конфига и ресурсов; прогон `cargo test` (26/26 зелёные)
и `cargo clippy --all-targets` (без предупреждений). Код не изменялся.

---

## 1. Итоговая оценка

Архитектурно решение сделано грамотно: чистое разделение слоёв (domain / service / adapter /
controller), всё вынесено за трейты, типы ПД — открытые строковые идентификаторы, расширяемые
конфигом, есть профили, переопределения по системам и маршрутам, шифрование маппинга,
circuit breaker, метрики, distroless-образ. Это хорошая заготовка под требование
«добавлять новые правила и сценарии без переделки всего сервиса».

Однако в текущем виде решение **не готово к нагрузочной/качественной автопроверке**: есть
несколько дефектов, которые ломают базовые сценарии — нумерацию плейсхолдеров (а значит и
демаскирование), разбор второго и последующих совпадений регулярок, демаскирование ответа LLM
в прокси-режиме и детектирование адреса. Три обязательных типа ПД вообще не имеют детекторов.

Условная готовность по требованиям ТЗ: **функционал ~55%, качество обработки — ниже заявленных
95%, SLA не подтверждён** (нет фактического таймаута запроса и нагрузочных замеров).

---

## 2. Что сделано хорошо

- Гексагональная структура, все зависимости — через трейты (`domain/traits.rs`), ручной DI в `main.rs`.
- `PdType` как открытый строковый тип + декларативные детекторы в конфиге (`ConfigRegexDetector`) —
  список ПД действительно расширяем без изменения кода.
- Конфиг: профили, `overrides` по системам, `route_overrides`, включение/отключение систем,
  вид маскирования на тип (`placeholder|partial|token|synthetic|hash|redact`), правила
  совместного появления (`PIN` маскируется только вместе с `CARD_NUMBER`) — это ровно тот
  «дополнительный плюс» из ТЗ, и он реализован.
- Криптография: AES-256-GCM, ключ сессии через HKDF, AAD, `Sensitive<T>` c `zeroize`,
  сравнение ключей систем в constant-time (`subtle`), секреты через `env:`/`file:`.
- Валидаторы контрольных сумм: Луна, ИНН-10/12, СНИЛС, календарная дата, серия паспорта.
- Нормализация текста с картой смещений norm → original (регистр, `ё`, тире, неразрывные пробелы,
  NFKC) — требование «идентификация не зависит от регистра» закрыто.
- Прод-гигиена: distroless + non-root, graceful shutdown по SIGTERM, `max_inflight`,
  понятные коды ошибок на русском, `.gitignore` с `target` (архив для автопроверки соберётся чистым).
- `cargo clippy --all-targets` проходит без предупреждений — автоматическая проверка качества кода,
  скорее всего, будет пройдена.

## 3. Блокеры (P0) — ломают основные сценарии

### 3.1. Нумерация плейсхолдеров считается по значению, а не по типу
`src/domain/entity.rs:98-103` — счётчик ведётся по ключу `(тип, канонич. значение)`:

- два **разных** человека в одном тексте получают **одинаковый** плейсхолдер `[ФИО_1]`;
- **один и тот же** человек, упомянутый дважды, получает `[ФИО_1]` и `[ФИО_2]`.

Последствия каскадные: в `Mapping` попадают две записи с одинаковым `key`, в `demask.rs:47`
`by_key.insert` перетирает первую → **при демаскировании восстанавливаются чужие персональные
данные**. Для модели теряется смысл (два разных клиента становятся одним, один клиент —
двумя). Поле `MaskState.assigned`, задуманное именно для «canonical → уже выданный номер»,
не используется вообще.
Это главный дефект: он бьёт сразу по двум критериям оценки — «сохраняется ли смысл запроса»
и «качество демаскирования». Тесты его не ловят, потому что во всех кейсах по одной сущности
каждого типа.

### 3.2. `captures()` вызывается по всему документу внутри цикла по совпадениям
`passport.rs:50`, `detect/mod.rs:91`, `card.rs:114,160,205`, `dates.rs:77`, `citizenship.rs:38,63`:

```
for m in self.re.find_iter(&doc.norm) {
    let caps = self.re.captures(&doc.norm).unwrap();   // ← всегда ПЕРВОЕ совпадение в тексте
```

Начиная со второго совпадения группы берутся от первого. Для CVV, PIN, имени держателя и всех
конфиг-детекторов позиция значения вычисляется из этих групп → **маскируется не тот фрагмент
текста**: настоящий CVV/ПИН остаётся в открытом виде, а вместо него вырезается кусок из начала
документа. Для паспорта неверно валидируется серия. Плюс это O(n·m) по времени: на тексте
в 100 000 токенов каждое совпадение заново сканирует весь документ.

### 3.3. Прокси-режим не демаскирует ответ LLM и теряет session_id
`proxy_handler.rs:113` вызывает `service.mask(..., None, ...)` — session_id генерируется и
**выбрасывается**, а ответ upstream возвращается клиенту как есть (`proxy_handler.rs:147-155`).
`route.response.demask` и `route.response.json_paths` из конфига не используются нигде.
Итог: в прокси-режиме потребитель получает текст с плейсхолдерами, а vault наполняется
записями, которые невозможно достать (утечка памяти до истечения TTL).

### 3.4. Адрес фактически не детектируется
- `address.rs:34`: регулярка улицы заканчивается ленивым `[\w\-. ]{1,40}?` — движок `regex`
  (leftmost-first) возьмёт минимум один символ, после чего `is_boundary` увидит следующую букву
  и отбросит кандидата. Улица почти никогда не попадает в компоненты.
- `address.rs:177-183`: ADDRESS собирается только если в цепочке **есть улица**. Нет улицы —
  нет адреса вообще.
- Компоненты (`ADDR_CITY`, `ADDR_STREET`, …) кладутся только внутрь `candidate.components` и
  никогда не публикуются как самостоятельные сущности → требование «адрес в т.ч. отдельно:
  страна, индекс, город, улица, дом, квартира» не выполняется. Настройка `mode: components`
  доходит до `EffectivePolicy.address_mode` и там не используется ни разу.

### 3.5. Вероятная паника при склейке компонентов адреса
`address.rs:160-168`: `&doc.original[last_end..comp.span.start]` выполняется **до** проверки
порядка, а регулярка города `(г\.|город|...)\s*[\w-]+(\s[\w-]+)?` умеет захватывать первое слово
следующего компонента (например, «г. Балашиха д. 12» → город = «г. балашиха д»). При перекрытии
компонентов получается срез с `start > end` → паника, а строкой ниже ещё и вычитание usize с
переполнением. Паника в обработчике роняет соединение без ответа клиенту (в метриках это
будет выглядеть как таймаут). Требует проверки тестом на адресах без запятой между компонентами.

### 3.6. Stateless-режим vault неработоспособен
`guard_service.rs:90-95`: в `mask_context` кладётся только `ciphertext`, случайный nonce
теряется. При демаскировании (`guard_service.rs:130-133`) подставляется `nonce: Vec::new()`,
а `Nonce::from_slice(&[])` в `aes-gcm` паникует на несоответствии длины. То есть единственный
режим, который позволил бы масштабироваться без общего хранилища, не работает.

### 3.7. HTTPS к upstream не поддерживается
`llm_client.rs:40` и `ner_http.rs:30` используют `HttpConnector`, хотя в `Cargo.toml` есть
`hyper-rustls`, а в конфиге `url: "https://llm.internal.bank/v1"`. Любой https-upstream вернёт
ошибку соединения. Для требования «защищённый контур» это ещё и вопрос ИБ.

### 3.8. Нет детекторов для трёх обязательных типов ПД
`BIRTH_PLACE` (место рождения), `PASSPORT_ISSUER` (орган, выдавший паспорт) и `DRIVER_LICENSE`
(серия и номер ВУ) объявлены в `pd_types` и включены в профиль `strict`, но ни встроенного,
ни конфигурационного детектора для них нет. Словари `cities.txt` и `issuing_authorities.txt`
грузятся в `CompiledConfig` и не используются. Типы из «дополнительных плюсов»
(загранпаспорт, полис ОМС, свидетельство о рождении, военный билет) — так же только в списке.

## 4. Важные дефекты (P1)

1. **Нет привязки сессии к системе-потребителю.** `main.rs:231`: `system_id = "pd-guard"` —
   константа, которая идёт и в HKDF, и в AAD. Плюс `GuardService::demask` явно игнорирует
   политику (`guard_service.rs:119-120`, `let _ = policy;`). Любая аутентифицированная система,
   получив чужой `session_id` (или `mask_context`), демаскирует чужие данные. Ограничение
   «демаскирование в зависимости от системы» работает только косвенно — через то, что при
   `demask: false` маппинг не сохраняется.
2. **Горизонтальное масштабирование невозможно.** Единственный рабочий vault — in-memory
   (`vault_memory.rs`), Redis-адаптер — заглушка (`vault_redis.rs:15`), stateless сломан (п. 3.6).
   При двух репликах демаскирование ломается на каждом втором запросе. Это прямо противоречит
   требованиям RPS 1000–2000 и отказоустойчивости.
3. **Риск OOM.** `max_entries: 1_000_000` в moka считает записи, а не байты; при текстах до
   100k токенов один маппинг может весить сотни килобайт → десятки гигабайт при TTL 900 с.
4. **Лимит тела обходится.** `process_handler.rs:68` читает только `Content-Length`
   (`unwrap_or(0)`), а `read_body` собирает тело без ограничения — запрос с chunked-кодировкой
   не лимитируется вообще.
5. **SLA не обеспечен механически.** `deadline` считается, но проверяется только перед вызовом
   NER (`pipeline.rs:81`); `tokio::time::timeout` вокруг обработки нет. Таймаут upstream — 60 с
   при требовании ≤1 с (`config.yaml:164`), и `llm_client.rs:61` игнорирует переданный deadline.
6. **Заявленные, но не реализованные настройки:**
   - `rate_limit_rps` — компилируется в `CompiledConfig`, нигде не применяется;
   - `policy.filters` — список фильтров профиля игнорируется, всегда работают все четыре;
   - `ner_on_failure: fail` — не реализовано, всегда деградация;
   - `ambiguous_ids` — не используется;
   - `heavy_text_threshold_bytes`, `log_entity_offsets`, `ner.max_windows_per_request`,
     `ner.trigger_words`, `routes[].stream: forbid` — парсятся и не читаются
     (триггер-слова NER захардкожены в `pipeline.rs:227`);
   - **горячая перезагрузка конфига — заглушка**: `main.rs:268` `reload: Arc::new(|| Ok(()))`,
     крейт `notify` не используется, `POST /admin/config/reload` возвращает 200 и ничего не делает.
     README при этом утверждает, что «сервис перечитывает файл автоматически» — расхождение
     документации и кода.
7. **`GET /metrics` всегда пустой.** `metrics.rs:19-21` создаёт новый рекордер на каждый вызов
   `render()`. Реальные метрики доступны только на порту экспортёра (9090). Заодно `/metrics`
   и `/health/*` отданы на публичном листенере без аутентификации (`router.rs:33-36`).
8. **NER-адаптер не сопоставляет смещения.** В `ner_http.rs:65` окна (координаты `doc.norm`)
   применяются к оригинальному тексту, ответ NER ожидается с абсолютными оффсетами без индекса
   окна, а полученные спаны не проходят через `doc.to_original` (`pipeline.rs:88`). При включении
   NER это даст маскирование по неверным позициям вплоть до паники на границе UTF-8.
9. **Ложные негативы из-за подстрочного поиска без границ слов:**
   - `inn.rs:53` и `relevance.rs:128`: «ао», «ип» ищутся как подстроки — слова «тип», «принцип»,
     «липецк», «хаос» превращают ИНН физлица в ORG_INN (не маскируется) и убивают кандидата ФИО;
   - `relevance.rs:23-28`: `f.contains(&orig)` — реальный клиент с фамилией/именем публичной
     персоны («Александр», «Пушкин») может быть признан непубличными данными и не замаскирован.
10. **ФИО: нет проверки смежности токенов.** `fio.rs:84-87` в список попадают только слова с
    флагами, промежуточные слова выбрасываются, а шаблоны применяются к соседям **по списку**.
    «Иванов позвонил. Иван Иванович ответил» склеится в одну сущность и будет вырезано целиком.
    Словарь имён — 108 записей, публичных лиц — 14: для эталонного датасета этого мало.

## 5. Производительность (риски под нагрузкой)

- Префильтр не вычисляется: `pipeline.rs:63` всегда передаёт пустой `DetectCtx::default()`,
  поля `keyword_hits`/`active_detectors` не заполняет никто. `context_ac` (AhoCorasick) и
  `detector_value_groups` в `CompiledConfig` мертвы. На каждый запрос гоняются все 15+ регулярок
  по всему тексту.
- `Document::new` (`document.rs:42-65`) аллоцирует `String` на каждый символ (nfkc → lowercase →
  normalize_char) и хранит `Vec<u32>` размером с текст в байтах — ×4 памяти. Для 100k токенов
  это сотни тысяч аллокаций на запрос.
- `DefaultResolver::resolve` (`resolve.rs:27-48`) — O(n²) по кандидатам; при этом `candidates.clone()`
  в `pipeline.rs:99` копирует весь вектор кандидатов ещё раз.
- `resolve_policy` вызывается на каждый запрос и клонирует профиль, labels, thresholds,
  priorities (`loader.rs:439-486`); поле-кэш `CompiledConfig.policies` создаётся пустым и не
  заполняется.
- Плюс квадратичное сканирование из п. 3.2.

Заявленные 1000 RPS при Latency ≤1 с на текстах до 100k токенов без устранения этих пунктов
подтвердить нельзя; нагрузочных замеров в репозитории нет (`benches/detection.rs` измеряет
только `Document::new`, детекция не бенчмаркается).

## 6. Мелкие замечания (P2)

- `validators.rs:250`: текущий год захардкожен (`2026 % 100`), при этом `(cur + 1) % 100`
  сломается на рубеже века. Крейт `time` уже в зависимостях.
- `mask.rs:209`: синтетический телефон собирается из 9 цифр вместо 10 (`+7 (999) 999-99-9`).
- `crypto.rs:99-104`: токен — 8 hex-символов (32 бита). Для детерминированной токенизации на
  больших объёмах коллизии вероятны, а коллизия = демаскирование в чужое значение.
- `proxy_handler.rs:171-175`: в bypass-режиме метод, URI и заголовки исходного запроса теряются
  (всегда `POST /`).
- `demask.rs:77-88`: подстановка по частично замаскированным значениям — линейный поиск по всему
  тексту для каждой записи, O(записи × длина).
- `loader.rs:228`: в сообщении о дублирующихся маршрутах индекс второго маршрута всегда `i+1`.
- `fio.rs:109-118`: список суффиксов содержит дубли («ова», «ева», «ской», «цкой»).
- `error_mapper`: `UpstreamTimeout` отдаёт код `UPSTREAM_ERROR` — потребитель не отличит таймаут.
- `process_handler.rs:237`: метрика ошибок пишется с пустыми лейблами system/route/operation.
- Тесты: нет ни одного теста HTTP-слоя (аутентификация, коды ошибок, лимиты), адреса,
  нескольких сущностей одного типа, прокси-режима; интеграционный тест дублирует сборку
  пайплайна из `main.rs` (расхождение уже есть — в тестах нет `SyntheticMasker`).
- Логирование: по требованию 2.1 нужно логировать **выявленные типы ПД** по каждому запросу;
  в лог пишется только их количество (`process_handler.rs:132-142`), типы уходят лишь в метрику.
  Сами значения ПД в логи не попадают — это сделано правильно.

| Ограниченный список систем | ✅ | ключи + enabled + 401/403 |
| Гибкая настройка типов/демаскирования/вида маски | ⚠️ | описано и компилируется, часть настроек не применяется (п. 4.6) |
| Инструкция по настройке ≤5 предложений | ✅ | в README, 5 предложений |
| Качество 95% | ❌ | не подтверждено; перечисленные дефекты гарантированно ниже |
| До 100 000 токенов | ⚠️ | лимит тела 2 МБ проходит, но производительность не подтверждена |
| Latency ≤1 с, RPS 1000 | ❌ | нет таймаута обработки и нагрузочных замеров |
| Масштабируемость | ❌ | только in-memory vault (п. 4.2) |
| Деградация при недоступности компонентов | ⚠️ | circuit breaker и degrade для NER есть; для vault — 503 без деградации |
| ПД не попадают в логи/метрики | ✅ | значения не логируются, `Sensitive` + zeroize |
| Токенизация/синтетика (бонус) | ⚠️ | реализовано, но синтетический телефон невалиден, токен 32 бита |
| Маскирование по комбинации типов (бонус) | ✅ | `combination.rules`, PIN+CARD_NUMBER |
| Прочие документы (бонус) | ❌ | только в списке типов |

## 8. Риски для автоматической проверки

1. **Контракт API не подтверждён.** Реализован собственный контракт
   `POST /process {operation, text, session_id, mask_context, route}`. Проверяющая система
   использует контракт из Приложения A онбординга — его нужно сверить дословно (имена полей,
   формат ответа, коды ошибок). Любое расхождение = нулевой результат прогона.
2. Демаскирование в прокси-режиме отсутствует — если проверка идёт через прокси, все ответы
   вернутся с плейсхолдерами.
3. Паника на адресах (п. 3.5) под нагрузкой даст обрывы соединений вместо ответов.
4. Для прогона нужен внешний `PDG_MASTER_KEY` и ключи систем; при отсутствии переменных
   окружения сервис не стартует (`loader.rs:276-292`) — нужен дефолт или понятный fail-fast
   в инструкции развёртывания.
